# 試験計画・公開判定基準

> 2026-10-26改訂（#23）: GPS不使用・写真地点自己申告へ移行。追加の端末限定写真案は未実装・Must変更/新同意承認待ち。画像は同じブラウザのIndexedDBに保存し、写真ID・地点・時刻だけBackendへ送る。旧クラウド写真の本人照会・削除・期限清掃は各`deleteAfter`まで別に検証する。未承認・未達なら実データを受け付けない。

## 目的

作品表現だけでなく、参加開始、写真撮影、地点選択、経路再構成、到着、停止、削除、障害復旧を本番条件で検証し、写真とチェックポイント地点を使って公開できるか判断する。

## 試験環境

- 開発環境: 合成データのみ。実データを持ち込まない
- ステージング: 本番と同じ認証・DB構成。短時間の同意済み実地試験のみ
- 本番: 承認済みドメイン、機材、ネットワーク、設定を使用
- 試験データ: 名前や実在人物と紐付かない合成セッションを原則とする

## 端末・条件マトリクス

対象はiOS 16.4以上とAndroid版Chrome 111以上とする（NFR-008）。必須の実機はiPhone 2台とメーカーの違うAndroid 2台とし、機種とバージョンを公開前に記入する。

| Android | メーカーの違う2台、対象の最古・最新Android、Chrome 111以上 |
| 回線 | 学内Wi-Fi、モバイル回線、両者の切替 |

## 経路・地点試験

- 実際に通った既知経路と、チェックポイント地点をつないだ最短経路を比較し、辺単位の一致率と誤選択を記録する
- 同距離の複数経路、地点間の遠距離、建物入口、階段、通行止めを試す
- 最後の写真からShibaLab（到着）までの区間が同じ線で描かれることを確認する
- 再生が全体10〜20秒に収まり、区間の長さに比例配分され、写真地点で少し停止することを確認する
- 地点の選び直し（再選択）の扱いは未決（TRACE_F#45）。未決のまま試験項目へ含めず、決定後に追加する

暫定合格値:

- 通行不能・立入禁止の辺を採用しない
- 再生時間が10〜20秒の範囲内で、区間ごとの配分が長さに比例する
- 実経路との辺一致率は改善指標として記録するが、一律の公開条件にはしない

## 写真試験

- iOS・Androidで縦、横、前後カメラ、高解像度画像を撮影する
- JPEG、WebP、非対応形式、拡張子偽装、破損画像、5MB超、1920px超を端末保存前に試す。メタデータAPIには画像を含むpayloadを送って拒否を確認する
- 同じブラウザに保存した画像にEXIF、GPS、端末情報、元画像サムネイルがないことと、新規画像のネットワーク送信が0件であることを確認する
- 12枚連続撮影、端末容量不足、IndexedDBの削除・早期消失、回線切断・復旧、同一`clientPhotoId`と冪等性キーの再送を試す。別ブラウザでは画像を復元しない
- 写真0枚、1枚、12枚で到着後の表示を生成する。0枚・1枚では簡易表示になることを確認する
- 写真単位削除後に前後RouteSegmentが再生成されることを確認する
- セッション削除と期限削除（TTL 6時間＋`delete_after`24時間、開発側既定）でサーバーのメタデータ・経路を確認する。端末が開いている場合の画像削除と閉じている場合の期限後残存・次回起動時削除を分けて確認する。旧写真object/縮小画像/派生物は期限まで本人取得・削除・期限清掃を確認する
- 端末画像の保存時間・容量・電池消費と写真メタデータ登録の通信量・所要時間を別々に記録する

暫定合格値:

- 対応端末で端末内写真保存成功率99%以上（提案値。実測・要件承認待ち）
- 写真撮影から端末保存とメタデータ登録までp95 10秒以内（提案値。通信再送時を除く）
- EXIF残存0件、新規画像の通信送信0件、描画への原写真送信0件
- サーバーメタデータ・旧クラウド写真の削除期限超過0件。閉じた端末の画像即時消去は保証しない

## 負荷・耐久試験

- 合成クライアント60セッションで、写真メタデータ送信と地点選択を含む参加フローを30分継続する
- 50セッション中に3人、5人、10人の同時到着を試す
- 20端末相当で写真メタデータを同時登録し、画像を送らずWSS配信と描画が継続することを確認する
- 60セッションが各12枚の写真メタデータを持つ容量試験を行う。画像は参加実機上でのみ合成テスト画像を使う
- 8時間の描画・Backend・DB連続運転を行う
- WebSocket切断・再接続を繰り返し、イベント重複と欠落を確認する
- DB容量80%相当、ログ出力先逼迫、遅い回線を試す
- 最大負荷時のDB総接続数、接続待ち、長時間query、lock待ちを記録する
- 最大1インスタンスのままBackendの再配置・再起動を行い、描画機の自動再接続と最新状態への復帰を確認する。複数インスタンスへのscale outは共有状態を実装してから別途試験する

50同時セッション・60セッション相当は試験条件であり、予測参加人数50人/日から導いた本番同時上限ではない。301教室の導線・回線・実機/負荷試験の結果をIssue #15に記録し、公開前に本番の最大同時参加人数を判断する。

暫定合格値:

- APIエラー率1%未満。ただし認証・入力拒否は除く
- サーバー起因のデータ欠落1%未満
- 到着演出成功率95%以上
- 通常負荷で到着待ちp95 30秒以内
- 8時間で手動再起動、メモリ枯渇、表示停止がない

## セキュリティ・プライバシー試験

- IDだけ、期限切れトークン、別セッションのトークンによる操作を拒否する
- セッション作成・到着APIのレート制限を確認する
- 巨大JSON、不正`checkpointId`、未来・過去時刻、重複送信を安全に拒否する
- 到着証明の改変、共有、再利用、期限切れを拒否する
- 描画通信、運営画面、アプリログ、サーバーログに緯度経度・生GPSがないことを検索する。参加端末のリクエストに座標がないことを確認する
- 描画通信、運営画面、ログ、参加端末のネットワークリクエストに新規写真の画像・画像URL・画像ハッシュ・寸法がないことを確認する
- 旧写真bucketの公開アクセス、一覧取得、期限切れ署名URL、別セッション認証を拒否する。新規画像用のアップロードURL発行を停止する
- 旧LivePresenceSessionのトークンで位置送信・`on_site`・他人の状態照会ができないことを確認する。旧GPSデータは`deleteAfter`まで保持され、前倒し削除されないことを確認する
- Push本文に位置・写真・参加記号がなく、無効subscriptionを自動削除することを確認する
- DBバックアップ（最大7日、提案値）、アクセスログ（30日、提案値）、監視サービスの保持期間を確認する。いずれも大学承認待ちであることを記録する
- local / staging / productionで資格情報・DB・旧写真bucket・暗号鍵が分離されていることを確認する
- 旧写真bucketのバージョニングが無効で、各`deleteAfter`での旧写真期限削除が働くことを確認する
- 運営資格情報でのみ運営操作が可能で、操作履歴が残ることを確認する

| migration・バックアップ復旧・接続上限・直前版ロールバック（T-024〜027） | DB担当がmigration/復旧/接続数を採取、リリース担当がmanifestを照合し再buildせず復帰、技術責任者が結果を確認 | stagingで承認済みバックアップと合成データを用いた復旧・期限清掃の継続を確認。本番昇格/戻しは承認済み手順・時間帯で版と開始/復帰時刻、ready状態、データ件数、予約接続枠の値を残す |
| WSS・Internet・Backend障害別の1分切替（T-010、公開判定） | 当日運営責任者が判断・切替を指示し運営担当が操作、描画担当が展示継続を確認 | まずstagingで障害を個別注入し、承認済み本番機材で切替リハーサル。各障害の検知・判断・指示・合成データ展示開始時刻、操作履歴、画面記録を残し、**判断から展示継続まで60秒以内**か判定する |

各行の試験記録は「試験ID/要件ID、状態（実施前・合格・不合格・保留）、日時・実施者/確認者、環境/機材/回線、データ承認者とデータ種別、release manifest版、手順・測定値/母数・判定閾値、関連する画面/メトリクス/ログの保存先、逸脱・再試験」を持つ。個人情報・写真原本・資格情報を証跡へ転載しない。未測定値や未指定担当は空欄として「実施前」のまま管理し、試験ごとの閾値と根拠を照合してから初めて合格とする。

全Mustの照合では、以下の既存T番号・章の証跡に対して`scope-requirements.md`の**各要件IDごと**に受け入れ条件を照らし、未試験・未決・不合格を一括で合格扱いしない。T番号だけでは条件を満たせない場合、記載の確認事項も試験記録に残す。

## 公開判定

次をすべて満たした場合だけ、写真とチェックポイント地点を使って公開する。

- 全Must要件に対応する試験が合格している
- 重大障害と重大プライバシーリスクが未解決でない
- 本番端末・ネットワーク・会場でE2Eを3回連続完了している
- 最大負荷、8時間耐久、通信断、描画停止、削除試験が合格している
- 新方式に対応する承認済み同意文・版と正本、端末画像の保存/消失と削除限界の説明、保存期間、問い合わせ先、当日責任者が承認済みである。旧`2026-memory-photo-no-gps-draft-1`を新方式の承認済み版とみなさない
- バックアップ描画と合成データ展示へ1分以内に切り替えられる
- 新規写真の端末保存・EXIF除去・メタデータだけの送信・写真単位/期限削除と、旧写真の非公開アクセス・本人取得・削除試験が合格している
- 経路グラフが主要導線で現地確認され、通行不能な辺を経路に採用しない
- PostgreSQL migration、バックアップ復旧、接続上限、直前releaseへのロールバック試験が合格している

未達の場合は、実データの受付を無効化し、合成データまたは写真なしの代替体験で公開する。

## 2週間の技術成立判定

本制作へ入る前に、次の縦切り試作を実機・現地で完了する。通知利用率は判定条件に含めない。

| Gate | 2週間で確認すること | Go条件 | No-Go時の縮小 |
|---|---|---|---|
| G-01 | iOS/Androidで撮影、EXIF除去、画像の同じブラウザへの保存、写真ID・`checkpointId`・撮影時刻だけの登録/再送 | 実機で端末保存とサーバーメタデータ受理、容量不足・画像消失・削除の成否分離、新方式の画像送信0件を検証 | 端末保存が成立しないなら写真実データ受付を停止し、代替展示とMust変更・同意の再承認を検討。無断でサーバー画像保存へ戻さない |
| G-02 | 3Dマップでの地点選択、Backendでの座標・ノードID解決 | 選択した地点が描画座標へ正しく解決され、端末から座標が送られない | 地点選択をスポット一覧からの一覧選択へ縮小する |
| G-03 | 写真地点からGraph経路を生成 | 禁止辺を使わず、最後の写真からShibaLabまでつながる | 経路を直線・抽象表現に縮小する |
| G-04 | 3D Map、Graphの版同期 | 主要基準点で許容誤差を決め、版不一致を拒否できる | 2D平面または限定エリアへ縮小する |
| G-05 | 到着QR検証、ArrivalEvent、0・1枚の簡易表示 | 到着が0枚・1枚でも成立し、簡易表示が崩れない | 簡易表示をスポット名の文言表示だけに縮小する |
| G-06 | 30分ごとの撮影リマインダーと到着での停止 | 購読・停止・解除が実機で明確に動く。通知なしでも参加できる | Pushを外し、画面内の撮影案内だけにする |

G-01〜G-06の結果、測定値、既知の制約、採用する縮小案を会議で承認してから3D表現の作り込みへ進む。
