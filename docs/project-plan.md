## 完成版の主要判断

| 判断 | 採用した設計 | 理由・制約 | 根拠 |
|---|---|---|---|
| 参加の中心 | GPSなしのMemory参加 | 自己申告地点で写真の節目をつなぐ。実際の歩行ログを再現したとは説明しない | [写真仕様](photo-memory.md)、[Frontend README](https://github.com/Mino829/TRACE_F/blob/be94bd2/README.md) |
| 新規画像の保存 | 端末内IndexedDBのみ | サーバーに送るのはmetadata。端末消失をBackendから復旧できない | [データモデル](data-model.md)、[Backend README](https://github.com/Mino829/TRACE_B/blob/6b87961/README.md) |
| 旧データ移行 | 新規書込みを止め、期限内の本人操作と清掃を残す | 旧Live・旧画像を会期終了だけで即時削除せず、既存同意・期限を保護 | [プライバシー](privacy.md) |
| 会場描画 | three.js `/display` | Unity / TouchDesignerとの比較未完了を現行仕様に残さない。実投影の受入記録は別途必要 | [システム構成](architecture.md) |
| 空間データ | 固定Graph・座標・3DMapの互換版 | IDが同じでも別版の座標へ読み替えず、参加時の版を保護 | [座標・Graph](coordinate-mapping.md) |
| 参加・運営の配置 | CloudflareサイトWorker＋Google Cloud東京 | 既存配信とGo/PostgreSQLを利用。Cloudflareを含む全処理が東京とは保証しない | [インフラ方針](infrastructure-database-decision.md) |
| 認証 | 本人Bearer、個人Google運営資格、描画資格、Edge秘密を分離 | 資格の用途・保持先・失効範囲を分ける。Googleログインだけで全管理APIを使えるわけではない | [API](api.md) |
| 到着と再視聴 | 初回到着と本人の新QR再視聴を分離 | 写真・参加・期限を作り直さずFIFO末尾へ。割込み・自動ループにしない | [状態遷移](state-machine.md) |
| 本人の作品 | 到着・会場再生から独立 | 閲覧だけで到着や通知方針を変更しない | [参加者ジャーニー](user-journey.md) |
| 撮影通知 | 任意のGo Web Push、30分 | 到着後継続は新同意方針の新規参加だけ。既存参加への一律延長をしない | [Backend通知契約](https://github.com/Mino829/TRACE_B/blob/6b87961/README.md) |
| 参加停止 | 再開不可の終端化、削除とは別 | 各`deleteAfter`まで本人閲覧・削除を残す | [データモデル](data-model.md)、[終了手順](deployment-operations.md#終了手順) |

これらはコードを確認した設計判断であり、採用日・正式承認日を推定して付与しない。Cloudflare＋Google Cloudへの技術配置方針は2026-10-21の設計記録を引き継ぐ。その他の判断経緯はソースのcommit・PRと[改訂前文書](https://github.com/Mino829/trace-campus-installation/blob/5626748/docs/project-plan.md)を参照する。

## 終了後の判断順序

1. 本番と旧検証系を識別し、現在の受付・通知状態を確認する。
2. 本人の期限内閲覧・削除と清掃に必要なAPI・DB・旧GCS依存を確認する。
3. 権限を持つ担当者が停止範囲を判断し、操作結果と残件を記録する。
4. 保持義務と共有アカウント内の他用途を確認してから費用停止・資源整理を判断する。
5. 撤収・精算・障害の記録を集め、再展示を行う場合だけ新しい計画を立てる。

詳細な操作境界は[配置・展示運用](deployment-operations.md)を正とする。旧計画の11月7日（T+1週）は当時の目安であり、承認済みの新期限や全データ一律の保持期限ではない。

## 保守・再展示の変更判断

- 本人の権利を優先し、受付・通知・展示・本人閲覧・削除・清掃を一つのスイッチで停止しない。
- mainへの文書反映でも既存CI/CDが動く可能性がある。実配備設定を確認し、文書改訂を公開操作の許可にしない。
- API・Graph・資格・同意・保持期間の変更は、影響するFrontend／Backendと設計を一緒に更新する。
- 再展示は採否、担当、費用、同意、受入条件を新しく判断する。GPS・クラウド写真・写真ピン等の旧案は自動的な次期要件にしない。
- 未確認の実績を仕様で埋めず、未実装機能を実装済みとして説明しない。
