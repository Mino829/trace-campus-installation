# 配置・展示運用・障害対応

## 推奨配置

```text
Vercel
  Next.js Web App
          |
          | HTTPS / WSS
          v
承認済みクラウドの東京リージョン（いずれか一方）
  第一候補: Google Cloud
    Cloud Run / Cloud SQL PostgreSQL / Cloud Storage / Monitoring
  代替: AWS
    Go container実行環境 / RDS PostgreSQL / S3 / CloudWatch
          |
          | outbound WebSocket
          v
Mac mini M4 または高性能ノートPC
  Unity / TouchDesigner
          |
          | HDMI / Audio / Control
          v
プロジェクター・音響・照明

運営ノートPC
  運営ダッシュボード
  到着キュー操作

Raspberry Pi 4B
  死活監視
  NFC・物理ボタン・LED制御候補
```

学内ネットワークから描画PCへの受信ポート開放を要求せず、描画PC側から公開サーバーへ接続する。

本番では承認済みクラウド環境のマネージドPostgreSQLだけを正本とし、写真は同じ承認済み地域の非公開オブジェクトストレージへ保存する。MVPからSQLiteを本番正本にせず、Google CloudではCloud SQL for PostgreSQL、AWSではRDS for PostgreSQLを使用する。Goは両環境へ配置できるOCI互換コンテナとし、提供者固有機能への依存を抑える。会場PC上のGo Backendは開発・緊急構成に限り、本番正本と同時書き込みしない。

通常GPSの最新表示位置はPostgreSQLへ履歴保存しない。単一BackendではGoメモリへ30〜60秒TTLで保持し、複数Backend化するときにRedis互換の共有TTLストアへ移す。詳細は[インフラ・データベース方針](infrastructure-database-decision.md)を正とする。

## 環境・リリース管理

- `local`、`staging`、`production`を分離し、本番参加者データを他環境へコピーしない
- pull requestごとにVercel Previewを作り、BackendとDB migrationは先にstagingで検証する
- productionは`main`へのpushだけで自動公開せず、技術責任者が承認した成果物を昇格する
- Web、Go container、DB schema、WebSocket schema、CampusGraph、座標変換、3D Mapの版をrelease manifestへまとめる
- DB migrationは後方互換のあるexpand-contract方式とし、production起動時に破壊的変更を自動実行しない
- T-1週以降は緊急修正以外を停止し、直前安定版へ戻せるWeb deployment、container image、描画ビルドを保持する
- Cloud RunまたはAWSのBackend最大インスタンス数と、Goの1インスタンス当たりDB接続上限を同時に設定する

## MVP性能目標

実地試験前の仮目標。

| 指標 | 目標 |
|---|---:|
| 同時追跡 | 50セッション |
| 位置送信間隔 | 5秒 |
| 有効位置をBackendが受信してから展示反映 | p95で2秒以内 |
| 写真撮影から保存完了 | p95で10秒以内 |
| PhotoMoment確定からRouteSegment生成 | p95で3秒以内 |
| 描画WebSocket再接続 | 10秒以内 |
| 到着演出時間 | 10〜20秒 |
| 描画 | 30fps以上 |
| 連続稼働 | 8時間 |

位置取得間隔が5秒のため、実世界の移動から表示までの総遅延は最大で取得間隔と通信遅延を含む。2秒目標はBackend受信後の処理・配信・描画だけを測る。

## 起動手順

1. インターネット、学内Wi-Fi、モバイル回線を確認する
2. GoのDB接続と `/health/ready` を確認する
3. 描画機を起動し、WebSocket接続を確認する
4. プロジェクター、解像度、音量、照明を確認する
5. 運営ダッシュボードで描画機がonlineになることを確認する
6. テスト端末でQR参加、位置送信、到着、再生、停止を通す
7. 写真撮影、非公開保存、本人用ストーリー、写真単位削除を通す
8. 写真ピン、3件フォトスポット、TTL、削除減算を通す
9. 到着後の停止と、追加同意による`on_site`エリア表示を通す
10. 座標・Graph・3D Mapの版一致と直前版へのロールバックを確認する
11. 写真ピン、フォトスポット、通知の個別停止を確認する
12. フォールバック映像へ切り替えられることを確認する
13. 新規受付停止、追跡停止、即時削除を確認する
14. 当日責任者、個人情報連絡先、障害連絡網を確認する
15. ケーブル養生、電源容量、非常口、音量、点滅注意を確認する

## 監視項目

- 追跡中セッション数
- 1分以内に位置更新されたセッション数
- WebSocket接続状態と最終heartbeat
- 到着キュー件数と最古待ち時間
- APIエラー率
- DB容量
- DB接続数、接続上限、長時間query、lock待ち
- DB自動バックアップ、point-in-time recovery、復旧試験の最終成功時刻
- 描画fps
- ネットワーク往復時間
- 位置受信から描画までのp95遅延
- 削除期限超過セッション数と削除ジョブ最終成功時刻
- ディスク、メモリ、CPU、プロセス再起動回数
- 写真アップロード成功率、処理時間、pending・failed・deleting件数
- オブジェクト容量、期限超過写真数、署名URL発行エラー
- 写真ピン発行数・期限超過数、フォトスポット数、少人数保護モード
- Push購読数、送信成功・無効subscription削除数。通知本文やendpointはログへ出さない
- `arrived`・`on_site`数と表示粒度。個別の移動履歴は表示しない
- 座標・Graph・3D Mapの公開版と描画機版、不一致拒否数

運営ログに生の緯度経度を出さない。セッションIDも画面では短縮表示する。

暫定アラート閾値:

- 主描画機heartbeatが30秒途絶
- 到着キューの最古待ちが30秒超過、または10件超過
- 5分窓のAPIサーバーエラー率が1%超過
- DB・ディスク使用率が80%超過
- DB接続使用率が承認済み上限の80%超過
- 削除ジョブが予定時刻から1時間以上未成功
- `pending`写真が15分以上、`deleting`写真が1時間以上残存
- 写真保存エラー率が5分窓で1%超過
- 描画fpsが30秒以上30fps未満

## 障害対応

| 障害 | 自動処理 | 運営対応 |
|---|---|---|
| インターネット切断 | 描画は最後の状態から自律表現へ移行 | 回線確認、保存済み映像へ切替 |
| Go停止 | 描画機が再接続を継続 | サーバー再起動、ready確認 |
| 描画ソフト停止 | watchdogが検知 | バックアップ描画機を接続 |
| GPS拒否 | Web AppがQRチェックポイントを案内 | 参加を強制しない |
| GPS精度低下 | 最終有効位置を30秒保持 | QRチェックポイントを案内 |
| 到着演出滞留 | タイムアウトでskip | キューを確認し手動skip |
| プロジェクター停止 | 音響または補助表示を継続 | 電源・入力・ケーブル確認 |
| 不正アクセス・生位置漏えい疑い | 新規受付と位置保存を停止 | 技術・個人情報責任者へ連絡し再開判断 |
| DB容量逼迫 | 新規受付を停止 | 不要ログ確認、正規の削除手順、容量拡張 |
| 削除ジョブ停止 | アラート | 原因調査、手動実行、期限超過範囲を記録 |
| 写真保存停止 | 写真受付を無効化しGPS体験を継続 | object権限・容量・回線確認、復旧後再送 |
| 写真公開設定・漏えい疑い | 写真取得と新規受付を停止 | bucket遮断、URL失効、個人情報責任者へ連絡 |
| 経路グラフ誤り | 該当辺を無効化し低信頼表示 | グラフ版をロールバックし再生成範囲を確認 |
| 写真ピンから個人推測のおそれ | 少人数保護モードまたは個別ピン停止 | フォトスポットのみ継続し設定を再審査 |
| Push誤配信・過剰配信 | 全通知停止 | 購読を無効化し原因・対象期間を確認 |
| 3D座標版の不一致 | 不一致イベントを破棄 | 位置描画を停止し直前の互換版へ戻す |
| 会場内GPS精度低下 | 点表示からエリア・操作時表示へ切替 | on_site位置表示を停止し演出だけ継続 |

## フォールバック展示

公開サーバーや位置取得が利用できなくても、作品が完全停止しない構成にする。

- 原則としてテスト用の合成軌跡を再生する。実軌跡をフォールバックへ転用しない
- 「リアルタイム接続なし」を運営画面には表示する
- 本番スクリーン上では障害メッセージではなく自律的な抽象表現へ切り替える
- 復旧後は `display.snapshot` を受け取り、自然にリアルタイム表示へ戻る

## 終了手順

1. 新規参加受付を停止する
2. 追跡中セッションを停止する
3. 到着キューを完了またはskipする
4. 展示用クライアントを切断する
5. DBバックアップの要否を確認する
6. 保存期間に従って位置情報を削除する
7. エラー件数と運用メモだけを記録する
8. 削除ジョブの成功と期限超過データがないことを確認する
9. 位置情報を含む一時ファイル、スクリーンショット、デバッグ出力がないことを確認する
10. 写真の期限超過、pending、deleting、公開オブジェクトがないことを確認する

## リハーサル受け入れ条件

- 主要導線を3回歩き、軌跡が3D空間と対応する
- 10台以上の実機で同時位置送信し、合成クライアントを含む60セッション負荷に耐える
- 3人、5人、10人の同時到着を処理できる
- 通信断から表示が自動復旧する
- 通常GPS履歴を保存・再送せず、停止後に最新表示位置が消える
- 到着後の停止と追加同意による`on_site`継続を選べる
- 写真ピン・フォトスポット・通知を別々に停止できる
- 座標・Graph・3D Mapの版不一致を描画せずロールバックできる
- 即時削除後と保存期限後に関連データを取得できない
- フォールバック展示へ1分以内に切り替えられる
- 本番構成で8時間連続稼働する
- 運営担当者だけで起動、受付停止、障害切替、終了を実施できる

詳細な公開判定は[試験計画・公開判定基準](test-plan.md)を正とする。

## 会場安全・導線

- 電源容量、接地、延長ケーブル、UPSの要否を会場担当者と確認する
- ケーブルを養生し、避難経路、車椅子導線、受付行列を塞がない
- プロジェクターの投射光を来場者が直接見続けない配置にする
- 音量上限、強い点滅、暗所の注意を確認し、必要な警告と代替導線を用意する
- 機材の排熱と自動スリープ、OS自動更新、通知表示を本番前に確認する
