# 配置・展示運用・障害対応

## 採用する配置（技術方針、公開承認前）

```text
Cloudflare サイトWorker
  Next.js静的Web、/log、/display
  /api/backend/* -> HTTPSでGoへ中継
          |
          v
Google Cloud東京
  Cloud Run: Go API（最大1インスタンス）
  Cloud SQL for PostgreSQL 17 / 旧写真用非公開Cloud Storage / Monitoring
          ^
          | 描画ブラウザの直接WSS（Googleログインで短期資格を取得）
          v
Mac mini M4 または高性能ノートPC
  Frontend /display（three.js）
          |
          | HDMI / Audio / Control
          v
プロジェクター・音響・照明

運営ノートPC
  運営ダッシュボード
  到着キュー操作

Raspberry Pi 4B
  死活監視
  NFC・物理ボタン・LED制御候補
```

学内ネットワークから描画PCへの受信ポート開放を要求せず、ブラウザからGo（Cloud Run）へ直接WSS接続する。Worker・会場PC上のagentは中継しない。本人確認はGoogleログイン＋許可メールとし、専用Originで短命描画資格を発行する。WSの最初のメッセージで資格と版を照合し、認証前はデータを送らない。方式・期限・失効条件は[API契約](api.md#描画websocket)を正とする。OAuth/Origin/許可メールの配備値、Frontendの資格更新・再接続、実Googleログイン・8時間実機試験・公開承認は未了である。Cloud Run IAMをこの実装のために無断で公開化しない。

本番では東京のCloud SQL for PostgreSQL 17だけをサーバー側データの正本とする。新規写真の画像バイト列は参加者のスマホ内（ブラウザのIndexedDB）にのみ保持し、Backendには写真ID・撮影時刻・参加者が選択した`checkpointId`等の経路再構成用メタデータだけを保存する設計目標であり、現行実装が移行済みという意味ではない。既存のサーバー写真は東京の非公開Cloud Storageにあり得るため、新規アップロードの停止後も各セッションの`deleteAfter`まで本人照会・削除と期限清掃に必要なbucket・鍵・読取/削除経路を維持する。Cloudflareを通る通信やログ、調査用D1/KVの東京処理・保存は保証されず、大学の審査と予算承認を終えるまで公開・実データ受付は行わない。GoはOCI互換コンテナとし、AWSへの変更は再決定する。会場PC上のGo Backendは開発・承認済み緊急構成に限り、本番正本と同時書き込みしない。
IndexedDBにはブラウザ・端末ごとの容量上限と消失リスクがあり、別端末への写真の自動移行はできない。端末を開かない間の自動消去も保証せず、参加者本人へ手動保存と削除方法を説明する。同意文の正本、参加者本人資格の発行経路、保存期間の緩和や大学承認は未決である。描画資格の方式決定をそれらの承認や公開可能の証明として扱わない。

2026-10-26の#23決定によりGPS取得・リアルタイム位置表示・`LivePresenceSession`新規発行は廃止した。写真地点は参加者が選択する`checkpointId`のみで表し、座標・対応ノードはBackendが解決する。既存の旧Sessionと旧GPSデータは廃棄済みではなく、各`deleteAfter`まで本人資格による照会・停止・削除と期限清掃を維持し、新規の位置送信・`on_site`は受け付けない。保持期間は大学承認待ち。

## 環境・リリース管理

- `local`、`staging`、`production`のWorker、Go、DB、旧写真用bucket、secret、データを分離し、本番参加者データを他環境へコピーしない。既存の`trace-staging-async5855`と`trace-staging-preview`は検証用であり本番ではない
- Cloudflareのプレビュー/サイトWorkerでWebを検証し、BackendとDB migrationを先にstagingで検証する。IAM保護中のCloud Run stagingへ共有secretだけで接続できないため、経路確認が済むまでは非公開を維持する
- productionは`main`へのpushだけで自動公開せず、技術責任者が承認した成果物を昇格する
- Web、Go container、DB schema、WebSocket schema、CampusGraph、3D Mapの版をrelease manifestへまとめる
- DB migrationは原則expand-contract方式とし、旧Session・旧GPSおよび既存のサーバー写真の本人照会・停止・削除と期限清掃を壊すテーブル・objectキーの破壊的削除は各`deleteAfter`まで実施しない。production起動時に破壊的変更を自動実行しない
- T-1週以降は緊急修正以外を停止し、直前安定版へ戻せるWorker配信、container image、描画ビルドを保持する
- Cloud Run最大1インスタンスとGoのDB接続プール上限を設定し、DBの管理/migration接続枠を残す。新旧revisionの並存にも注意する

独自ドメインはFrontend #30の選定・調達後にCloudflare DNS/TLSへ接続する方針。Cloudflare側のWAFと入口のレート制限、Go側の参加者単位のレート制限を併用し、Worker・Cloud Run・Cloud SQL・旧写真用bucketの異常を監視する。DNS/TLS・WAF・監視の実作業者および通知先は公開前に技術責任者が記録する（技術責任者はMino829。2026-10-26に企画・課金責任者との兼務で決定）。課金責任者Mino829がドメイン、Cloudflare、Google Cloudの見積もりと5,000円の上限を確認する。予算アラートは強制停止ではない。

## 起動手順

1. インターネット、学内Wi-Fi、モバイル回線を確認する
2. GoのDB接続と `/health/ready` を確認する
3. 描画機を起動し、WebSocket接続を確認する
4. プロジェクター、解像度、音量、照明を確認する
5. 運営ダッシュボードで描画機がonlineになることを確認する
6. テスト端末でQR参加、カメラ許可、写真地点`checkpointId`選択、署名・期限付き到着QR読取、経路再生、参加停止を通す
7. 移行後の設計目標として、画像をIndexedDBへ端末内保存し、Backendに写真ID・撮影時刻・`checkpointId`等のみを登録し、本人用ストーリーと端末内画像・サーバーメタデータの写真単位削除を通す。旧サーバー写真も別途本人照会・削除を通す。現行実装での達成済みチェックではない
8. 写真地点とCampusGraph最短経路、ShibaLab到着区間、サーバーメタデータ・経路の同一期限清掃、旧サーバー写真の期限清掃を確認する
9. 写真0枚・1枚の場合の到着と簡易表示、到着後の通知停止を確認する
10. CampusGraph・3D Mapの版一致と直前互換版へのロールバックを確認する
11. 撮影通知の個別停止と、旧Sessionの本人照会・停止・削除および期限清掃を確認する
12. フォールバック映像へ切り替えられることを確認する
13. 新規受付停止、参加停止、本人による即時削除を確認する
14. 当日責任者、個人情報連絡先、障害連絡網を確認する
15. ケーブル養生、電源容量、非常口、音量、点滅注意を確認する

## 監視項目

- 有効なMemorySession数と受付停止状態
- WebSocket接続状態と最終heartbeat
- 有効な到着待機キュー件数（`queued`のみ、上限50件）・最古待ち時間・演出skip数・満杯503件数。通常待機の30秒超過は自動skipせず、アラート閾値と障害時は公開前に決める
- APIエラー率
- DB容量
- DB接続数、接続上限、長時間query、lock待ち
- DB自動バックアップ、point-in-time recovery、復旧試験の最終成功時刻
- 描画fps
- 写真地点選択から経路再生までの処理遅延
- 削除期限超過セッション数と削除ジョブ最終成功時刻
- ディスク、メモリ、CPU、プロセス再起動回数
- 移行後のサーバー写真メタデータ登録失敗・削除期限超過（端末内画像の保存失敗は端末で確認する）
- 旧サーバー写真の`pending`・`failed`・`deleting`件数、object容量、期限超過数、本人取得/削除エラーと署名URL発行エラー（各`deleteAfter`まで）
- 写真地点・経路再構成エラー数と版不一致拒否数
- Push購読数、送信成功・無効subscription削除数。通知本文やendpointはログへ出さない
- 到着済みMemorySession数（公開画面では個別の地点・時刻・セッションIDを表示しない）
- CampusGraph・3D Mapの公開版と描画機版、不一致拒否数

運営ログに写真地点の大量列挙、旧GPS、画像URLや参加トークンを出さない。セッションIDも画面では短縮表示する。

暫定アラート閾値:

- 主描画機heartbeatが30秒途絶
- 到着待機キュー件数・最古待ち時間と`ARRIVAL_QUEUE_FULL`を監視する。待機50件の満杯時は新規到着を503・再試行可能とし、既存待機を維持する。Backend Draft PR #36で実装したが、配備・Frontend結合・アラート閾値・障害時の運用は未完了
- 5分窓のAPIサーバーエラー率が1%超過
- DB・ディスク使用率が80%超過
- DB接続使用率が承認済み上限の80%超過
- 削除ジョブが予定時刻から1時間以上未成功
- 旧サーバー写真の`pending`が15分以上、`deleting`が1時間以上残存
- 移行後のメタデータ登録エラー率が5分窓で1%超過。端末内画像の保存失敗はサーバー監視だけで検知できないため、端末上の失敗表示と実機試験で確認する
- 描画fpsが30秒以上30fps未満

## 障害対応

| 障害 | 自動処理 | 運営対応 |
|---|---|---|
| インターネット切断 | 描画は最後の状態から自律表現へ移行 | 回線確認、保存済み映像へ切替 |
| Go停止 | 描画機が再接続を継続 | サーバー再起動、ready確認 |
| 描画ソフト停止 | watchdogが検知 | バックアップ描画機を接続 |
| カメラ拒否・読取不能 | Web Appが参加条件と設定変更方法を案内 | 到着QRの表示・照明・端末を確認し、参加を強制しない |
| 到着演出滞留 | タイムアウトでskip | キューを確認し手動skip |
| プロジェクター停止 | 音響または補助表示を継続 | 電源・入力・ケーブル確認 |
| 不正アクセス・写真地点・旧GPSデータ漏えい疑い | 新規受付と該当データへのアクセスを停止 | 技術・個人情報責任者へ連絡し、旧Sessionの本人照会・停止・削除を維持できる復旧策を判断 |
| DB容量逼迫 | 新規受付を停止 | 不要ログ確認、正規の削除手順、容量拡張 |
| 削除ジョブ停止 | アラート | 原因調査、手動実行、期限超過範囲を記録 |
| 移行後の端末内写真保存失敗 | 端末上で失敗を表示し、未保存画像を保存済みと扱わない | 端末空き容量・ブラウザ設定を確認し、参加者に手動保存の選択肢を案内する。再撮影を強制しない |
| 旧サーバー写真の保存・取得・削除障害 | 旧写真への新規書込は移行後停止し、既存写真の本人照会・削除と期限清掃は維持する | bucket・鍵・権限・容量・回線を確認し復旧する。各`deleteAfter`より前にbucketや鍵を撤去しない |
| 旧写真bucketの公開設定・漏えい疑い | 旧写真取得と新規受付を停止 | bucket遮断、URL失効、個人情報責任者へ連絡し、本人照会・削除を復旧する |
| 経路グラフ誤り | 該当辺を無効化して経路再生を停止 | グラフ版をロールバックし再生成範囲を確認 |
| Push誤配信・過剰配信 | 全通知停止 | 購読を無効化し原因・対象期間を確認 |
| CampusGraph・3D Mapの版不一致 | 不一致イベントを破棄 | 経路描画を停止し直前の互換版へ戻す |

## フォールバック展示

公開サーバーや写真地点の再構成が利用できなくても、作品が完全停止しない構成にする。

- 原則としてテスト用の合成経路を再生する。実参加者の経路をフォールバックへ転用しない
- 「リアルタイム接続なし」を運営画面には表示する
- 本番スクリーン上では障害メッセージではなく自律的な抽象表現へ切り替える
- 復旧後は `display.snapshot` を受け取り、経路再生の接続状態を復元する

## 終了手順

1. 新規参加受付を停止する
2. 参加中のMemorySessionで新規登録を停止する（既存データの本人照会・削除は各`deleteAfter`まで維持する）
3. 到着キューを完了またはskipする
4. 展示用クライアントを切断する
5. DBバックアップの要否を確認する
6. 新規設計ではサーバーの写真ID・撮影時刻・`checkpointId`等と経路・削除冪等性記録を同じ`deleteAfter`期限で清掃する。端末内画像の期限処理は端末を開かない間の自動消去を保証しないため、本人による手動保存・削除の案内と合わせて検証する。旧サーバー写真と旧GPSデータ・旧Sessionは前倒し削除せず、各`deleteAfter`まで本人照会・停止・削除と期限清掃を続ける
7. エラー件数と運用メモだけを記録する
8. 削除ジョブの成功と期限超過データがないことを確認する
9. 旧GPSや写真地点を含む一時ファイル、スクリーンショット、デバッグ出力がないことを確認する
10. 旧サーバー写真の期限超過、pending、deleting、公開オブジェクトがないことを確認する。旧写真用bucket・鍵は全対象の期限清掃と本人対応の終了確認前に撤去しない

## リハーサル受け入れ条件

- 参加者が選択したチェックポイント地点と、再構成した経路の3D表現の対応を合成データで検証する。現地確認は公開前の必須試験であり、実施済みとは扱わない
- 想定同時MemorySession数の負荷は#15の人数確定後に試験する。完了済みの現地試験とは扱わない
- 写真0枚・1枚でも到着でき、2枚以上で写真間の経路と最後からShibaLabへの経路を再生できる
- 通信断から表示が自動復旧する
- 新規GPS取得・位置送信・`on_site`を受け付けず、旧Sessionは各`deleteAfter`まで本人照会・停止・削除と期限清掃ができる
- 新規設計では写真メタデータ・地点・経路・削除冪等性記録を同一期限で清掃し、端末内画像の削除・手動保存案内を確認する。旧サーバー写真の本人取得・削除と期限清掃も各`deleteAfter`まで試験する
- CampusGraph・3D Mapの版不一致を描画せずロールバックできる
- 即時削除後と保存期限後にサーバーの関連データを取得できず、旧サーバー写真も取得できない。端末内画像は端末が開かれない間の自動消去を保証しない
- フォールバック展示へ1分以内に切り替えられる
- 本番構成で8時間連続稼働する
- 運営担当者だけで起動、受付停止、障害切替、終了を実施できる

詳細な公開判定は[試験計画・公開判定基準](test-plan.md)を正とする。

## 会場安全・導線

- 電源容量、接地、延長ケーブル、UPSの要否を会場担当者と確認する
- ケーブルを養生し、避難経路、車椅子導線、受付行列を塞がない
- プロジェクターの投射光を来場者が直接見続けない配置にする
- 音量上限、強い点滅、暗所の注意を確認し、必要な警告と代替導線を用意する
- 機材の排熱と自動スリープ、OS自動更新、通知表示を本番前に確認する
